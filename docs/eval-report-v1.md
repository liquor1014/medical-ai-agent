## 3. 指标口径

1. **Recall@5**：`mean(|gold_chunk_ids ∩ top5_ids| / |gold_chunk_ids|)`。单条 gold 为 1 个片段时等价于 Hit@5，另单独上报 HitRate@5；本次两者均为 1.0（40/40）。
2. **SQL 执行准确率**：对 gold SQL 与生成 SQL 都调用 `guard_sql`（注入相同租户过滤）后只读执行；比较列数 + 行多重集合，忽略列名与行序，`Decimal/float` 统一保留 2 位小数、日期转 ISO 字符串。生成状态为 `rejected/failed` 或结果集不等即判 0。
3. **答案准确率**：走 RAG 路径（检索 → LLM 生成），回答对 `expected_keywords` 覆盖率等于 100% 记为正确（每个要点支持 `|` 分隔的同义写法，比较时忽略空白）；同时上报平均覆盖率。
4. **P95 延迟**：逐条端到端计时，最近秩法取分位；按“总体、retrieval、sql、answer”分别统计。
5. 意图路由准确率：用生产 `classify()` 对题目做离线分类统计，作为诊断项，不影响上面的能力指标。

## 5. 关键发现

### 5.1 RAG 上下文未注入真实模型（P0，已修复）

`ModelRouter.chat_stream()` 虽然接收 `context` 参数，但只把 context 传给 mock 分支，真实模型收到的是未加工的 `messages`。因此真实 DeepSeek 从未看到检索片段，回答依赖模型先验知识，出现“文档写 7 天却回答 14 天”“文档写 4 小时却回答 10 分钟”等与知识库冲突的答案，且同一数据集两轮答案准确率为 0.50 / 0.65，无法复现。

修复：在 `app/llm/providers.py` 增加 `_with_context()`，把检索上下文拼入 system 消息后再调用真实提供者。修复后答案准确率由不可复现的 0.50 / 0.65 提升到 0.85 / 0.85；继续修复检索排序（§5.2）后达到 1.00 / 1.00，两轮逐条判定完全一致。修复前后延迟略有上升，来自变长的提示词。

### 5.2 检索排序按主键而非相关度（P0，已修复）

`retrieval_agent.retrieve()` 原实现使用 `ILIKE` 命中关键词后 `ORDER BY id DESC LIMIT 5`，而非按匹配度排序。评测中 14 条失败样本的 gold 片段 **全部** 能在“按关键词命中数排序”的诊断检索中进入 top-5（诊断 Recall@5 = 1.0），说明下限由排序逻辑造成，不是召回能力不足。

修复：`SELECT` 中增加 `CASE WHEN content ILIKE ...` 累加得到 `hit_score`，排序改为 `ORDER BY hit_score DESC, id DESC`（同分时新片段优先，保证结果确定）。修复后 Recall@5 由 0.65 提升到 1.0（40/40），连带答案准确率由 0.85 提升到 1.0。后续 Qdrant 集合就绪后可直接切换向量检索，接口不变。

### 5.3 意图路由偏弱（P1，已修复）

修复前：SQL 类题目仅 87.5% 被分到 `nl2sql`，如“列出全部科室名称”“查询物资名称和单价”因不含统计关键词被分到 retrieval；答案类题目仅 50% 被分到 `retrieval`，凡含“多少”的文档问题（如“压力蒸汽灭菌的温度和时间分别是多少”）都会被 `nl2sql` 关键词抢先命中，实际运行走 SQL 后返回“无匹配数据”。

修复：`router_agent.classify()` 改为“报表 > 文档问答 > 数据查询”的优先级，文档类关键词由 10 个扩展到 54 个（验收、灭菌、有效期、储运、对账、追溯等），使文档问题不再被“多少”抢走；同时补充“查询/列出/金额/库存/合计”等数据查询词，覆盖不带“统计”字样的查询。修复后 100 条评测集路由全部正确（SQL 40/40、检索 40/40、答案 20/20）。

该方案仍是关键词表，未收录的新领域词会回落到默认 retrieval；后续可替换为分类小模型。

### 5.4 答案准确率受检索上限约束（已解除）

上下文注入修复后仍有 3 条答案失败（A01 24 小时、A02 5 分钟、A17 每年复审），均因 gold 片段未被召回（top-5 中不含 90005/90012/90024），模型按提示回答“资料不足”。修复 §5.2 排序后，20 条答案题全部通过，说明答案质量当前的上限就是检索质量。

### 5.5 SQL 执行准确率 40/40

生成 SQL 与 gold SQL 的结果集完全一致，未出现越权、超时或语法错误，说明 `guard_sql` 的租户注入与只读约束工作正常。需注意数据集以单表/两表模板化查询为主，难度有限；后续应补充多表关联、口径歧义、时间窗口类难题。

## 6. 指标复现性

- 数据集固定（sha256 校验）、语料固定 ID、`temperature=0`、模型路由固定，三项准确率指标两轮完全一致（1.00 / 1.00），逐条通过项差异为空。
- P95 属延迟指标，受公网模型响应波动影响：本轮两轮 P95 为 1.38 s / 1.32 s，P50 为 0.90 s / 0.85 s，差异约 5%，明显小于含冷启动的首轮波动。延迟结论只保证量级，不保证逐毫秒一致；报表同时给出 P50 与分任务延迟便于横向对比。
- 复现命令（在 `ai-service` 目录执行）：

```powershell

.\.venv\Scripts\python.exe -m app.eval.run_eval
.\.venv\Scripts\python.exe -m app.eval.run_eval --out ..\data\eval\eval_results_v1_repeat.json
```

- 复现前提：`.env` 中 DeepSeek Key 可用、Postgres 中 `hospital-demo` 演示数据未变更、`eval-bench` 语料已 seed。

## 7. 已知限制

1. 答案判分为关键词覆盖，对否定句和同义改写不敏感（如“不实行零库存管理”仍可能命中“零库存”），后续可引入“要点 + 否定词”规则或 LLM 判分并人工抽检。
2. 检索语料为评测专用合成文档，规模 40 片段，Recall@5 的绝对值不能直接外推到真实文档库。
3. SQL 评测样本偏模板化，1.0 的准确率不代表复杂业务口径下同样表现。
4. 延迟数据来自本机 + 公网 API，不含生产并发压测结论。
5. 意图路由为关键词表方案，评测集内的 100 条全部命中，但新领域词汇可能回落到默认 retrieval；后续应替换为分类模型并补充路由专项评测集。
